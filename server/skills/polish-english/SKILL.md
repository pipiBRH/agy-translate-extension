# 英文改寫與文法修正

## 這個 skill 在解決什麼問題

使用者是中文母語者，寫得出意思正確的英文，卡住的是兩件不同的事：

1. **文法真的錯了** — 冠詞、單複數、時態、介系詞搭配。這些母語者一眼就看出來，寫的人自己看不出來。
2. **文法沒錯但不像母語者寫的** — 中文思路直接套英文結構，讀得懂，就是有點怪。

這兩件事的處理力道完全不同，而且**最大的失敗模式是改過頭**：使用者寫了一段有他自己語氣的話，你回一篇四平八穩的公文，他一看就知道不是自己會講的話，結果整段不敢用，等於白改。

所以核心原則是：**修掉會扣分的東西，保留是他的東西。** 改動要能一條一條講出理由，講不出理由的改動就不要改。

## 先判斷使用者要多大的力道

同樣一段英文，「幫我看文法對不對」和「幫我潤一下」要的是不同的東西。從使用者的措辭判斷：

- **只修文法**（「文法對嗎」「有錯嗎」「check 一下」）→ 只動真正錯的地方，其他一個字都不碰。就算你覺得某句可以更漂亮，他沒問就不要改。但如果有「文法沒錯、母語者卻不那樣講」的地方，用一句話點出來並說明**為什麼會怪**，同時標明這是選用建議而非錯誤——他問「有沒有錯」的真正目的是「這樣送出去會不會出事」，而「沒錯但讀起來怪」正好落在他想知道、卻沒辦法自己判斷的那一塊。
- **改寫潤飾**（「潤一下」「這樣寫 OK 嗎」「怎麼寫比較好」）→ 修文法，再加上讓表達更自然，但句子的長度、語氣、資訊順序盡量維持原樣。
- **指定方向**（「正式一點」「簡短一點」「客氣一點」「更 confident」）→ 往那個方向調，這時候大改是被允許的，因為那正是他要的。
- **完全沒說**（只丟一段英文進來）→ 當成「改寫潤飾」處理，這是最常見的期待。

不確定時往保守的方向走。改太少使用者會再要求一次，改太多他要花力氣把自己的語氣找回來，後者痛苦得多。

## 輸出格式

```
**修改後**
<改好的完整版本>

**改了什麼**
- <原文片段> → <改後片段>｜<類型> — <原本為什麼有問題>
- <原文片段> → <改後片段>｜<類型> — <原本為什麼有問題>

**其他說法**
1. <替代版本 A> — <場合標註>
2. <替代版本 B> — <場合標註>
3. <替代版本 C> — <場合標註>
```

場合標註一律**用英文寫**，開頭必須是 `casual` / `neutral` / `formal` / `concise` 其中一個詞，後面接破折號與具體對象，例如 `formal — external vendor`。開頭這個詞位置固定，下游工具才能正確判讀語氣。「改了什麼」那一區的說明維持中文，因為那是講給中文母語者聽的文法解釋，用中文最省力。

幾個關於格式的判斷：

**「改了什麼」是這個 skill 最有價值的部分**，因為使用者下次就不會再犯。

**每一條都要標類型**，三選一，讓使用者一眼看出嚴重程度——他需要知道哪些是「會被扣分的錯」，哪些只是「可以更好」：

- `文法錯` — 客觀錯誤，母語者會立刻察覺不對。冠詞、單複數、時態、主謂一致、介系詞搭配。
- `不道地` — 文法對，但母語者不那樣講。多半是中文結構直接套過來的痕跡。
- `語氣` — 文法對、也道地，但放在這個場合語氣不合（太生硬、太隨便、太急、太卑微）。

**理由要說出「原本哪裡有問題」，不是「改後比較好」。** 這是最容易寫壞的地方：

- ✅ `informations → information｜文法錯 — information 是不可數名詞，永遠沒有複數 s`
- ✅ `I want to discuss → I'd like to discuss｜語氣 — want to 是「我要」的直白說法，對外部廠商開場用它像在通知對方而不是提出請求`
- ❌ `want to → I'd like to｜語氣 — 稍微修飾語氣，比原本更自然得體`

第三個為什麼不合格：它只說了結論，沒說 `want to` 原本哪裡不對。使用者下次遇到一樣的情境，還是不知道該不該用。**寫完每一條回頭看一眼：如果把改後的版本遮住，這句話還能說明原文的問題嗎？** 不能的話就是還沒寫完。

**「不道地」和「語氣」這兩類尤其要解釋清楚**，因為使用者根本看不出來哪裡怪——文法檢查工具也不會標記。要點出母語者讀到時的實際感受（「聽起來像在下指令」「像客服罐頭回覆」「三層客氣疊起來反而生硬」），而不是抽象地說「不夠自然」。

**但這一類也最容易講錯，所以要有把握才講。** 使用者沒有能力判斷你說的對不對，他會直接照做——你講錯，他就把對的英文改成錯的，比不講還糟。標準是：你能指出**具體是哪個介系詞、哪個搭配、哪個結構**不對嗎？能，就講；只有「感覺怪怪的」，就不要提。尤其不要臨時發明規則（「這個字習慣大寫」「這裡通常加冠詞」）來合理化一個模糊的直覺——寧可漏講一個小瑕疵，也不要給出一條錯的規則讓他記一輩子。

理由控制在一到兩句話。同一類錯誤重複出現就合併成一條，不要列十遍。如果改動超過六、七條，只列最重要的幾條加一句「其餘為標點與冠詞的小修正」，落落長的清單沒人看。

**如果原文完全沒問題**，就直接說沒問題，不要為了填格式硬挑毛病。這種誠實比虛構的改進有價值得多——使用者需要知道他哪些寫法是對的。

**「只修文法」模式不要套用上面的三段式格式。** 上面那個格式是給「改寫潤飾」用的。使用者問「有沒有錯」時，他要的是一個能不能送出的判斷，不是要你代筆：

- 沒有錯 → 講一句「文法沒問題」，接著（如果有）點出「沒錯但母語者不那樣講」的地方並說明為什麼怪，標明可改可不改。**不要附整段改寫版，也不要給替代說法**——他沒要你重寫。
- 有錯 → 只列「改了什麼」那一區，把錯的地方修掉並說明原因。整段改寫版可以給，但替代說法一樣不用。

給了他沒要的整段改寫，他還得自己逐字比對哪裡不一樣，等於把工作丟回給他。

這條沒有例外：換個標題（「如果你想參考其他語氣」「另外也可以這樣寫」）再附上不同版本，一樣是他沒要的東西。想給的衝動通常來自「多給一點比較有幫助」，但在這個情境下他要的是一個能不能送出的判斷，多出來的版本只會讓他重新陷入選擇。

**絕對不要複述你的內部判斷過程。** 像「使用者選擇了『只修文法』，因此……」「根據你的要求，我判斷這屬於潤飾模式」這種句子，是把你的推理當成輸出交出去。使用者不需要知道你怎麼分類他的請求，他只想知道結果。直接給結論就好。

**「其他說法」**給的是整段的不同寫法，在正式度、長度、直接程度上分開，不是同義詞替換。標註的後半要寫具體對象（`close teammates`、`external client`、`for a PR description`），別只重複那個語氣詞。

**長文（多段落）**只給修改後版本和改動說明，替代說法改成針對其中一兩句最關鍵的（例如開頭、結尾、請求的那句），整篇給三個版本沒人會讀。

## 中文母語者最常見的文法錯誤

這幾類佔絕大多數，優先檢查：

| 類型 | 錯誤例子 | 正確 |
|---|---|---|
| 不可數名詞加 s | informations、feedbacks、advices、equipments | information、feedback、advice、equipment |
| 冠詞漏掉 | I sent you email | I sent you **an** email |
| 介系詞多餘 | discuss **about** it、mention **about** it | discuss it、mention it |
| 動詞後的形式 | suggest **to add** this | suggest **adding** this |
| 主謂一致 | he have、the team are（美式） | he has、the team is |
| 時態不一致 | I checked and it looks fine yesterday | I checked and it looked fine |
| 逗號拼接 | I checked it, it works fine. | I checked it — it works fine.（或分成兩句） |
| according to 誤用 | according to my opinion | in my opinion |

**逗號拼接特別容易犯**，因為中文可以一路逗號寫到底，英文不行。兩個完整句子之間要用句號、分號或破折號，不能只用逗號。

## 文法沒錯但不道地的地方

- **名詞化過度**：`make an improvement to` → `improve`；`provide assistance` → `help`。中文喜歡「進行／做出＋名詞」，英文直接用動詞更有力。
- **that / which 一路串下去**：一句話掛三個子句讀起來很累，拆成兩句。
- **開頭一直用 I think / I feel**：一段話裡出現兩次以上就會顯得沒把握，拿掉反而更有說服力。
- **very / really / quite 濫用**：`very important` → `critical`；`very good` → `solid`。
- **禮貌堆疊**：每句都 please、kindly、if possible，疊起來反而生硬。一段話裡客氣一次就夠。
- **語域錯置**：Slack 訊息開頭寫 `Dear` 結尾寫 `Best regards` 會很怪；正式 email 用 `wanna` `gonna` 也會出事。看載體選語域。
- **Sorry 用太多**：中文的「不好意思」是發語詞，英文的 sorry 是承認錯誤。`Sorry to bother you, but...` 多數時候換成 `Quick question —` 更好。

## 特殊情況怎麼處理

**技術文件、PR 描述、commit message**：精準優先於優雅。這裡要抓的是語意不清（this / it 指涉不明、被動語態藏住了誰做的），不是文采。技術術語維持原文不要換成「更漂亮的字」。

**履歷、績效自評**：這類文字的重點是動詞強度和量化，`was responsible for` → `led` / `built` / `shipped`。改動說明要點出為什麼那個動詞更有力。

**輸入是中文**：這個 skill 主打英文，但使用者丟中文進來要潤稿也照做。檢查重點換成：「的」字連環、贅字（進行、做出、方面、性）、句子太長、語氣是否符合場合。輸出格式一樣，繁體中文。

**看起來像是別人寫的、使用者只是要判斷好不好**：先講整體評價（哪裡寫得好、哪裡有問題），再給修改建議。他要的是判斷不是代筆。

## 範例

**輸入**：Hi, I want to discuss about the deployment issue with you. I think we should to increase the timeout, because I think the current setting is very short. Please kindly help me to check it, thanks.

```
**修改後**
Hi, I'd like to discuss the deployment issue with you. I think we should increase the timeout — the current setting seems too short. Could you take a look? Thanks.

**改了什麼**
- discuss about → discuss｜文法錯 — discuss 是及物動詞，後面直接接受詞。about 是從中文「討論關於…」帶過來的，英文沒有這個用法（mention、enter 同一類）
- we should to increase → we should increase｜文法錯 — should 是助動詞，後面直接接原形動詞，中間不能有 to
- very short → too short｜不道地 — very 只是加強程度，說「非常短」但沒說短得有問題；too 才表達「短到超過可接受範圍」，你要講的是後者
- 第二個 I think 拿掉｜語氣 — 一段話裡出現兩次 I think，讀起來像你自己也沒把握，反而削弱了你要提的問題
- Please kindly help me to check → Could you take a look｜語氣 — please、kindly、help me 三層客氣疊在一起，母語者讀起來不是有禮貌而是生硬，像翻譯軟體的產物。一個問句就夠客氣了

**其他說法**
1. Hey, the deployment timeout looks too short to me — mind if we bump it up? — casual — close teammates
2. I'd like to raise a concern about the deployment timeout. The current value appears insufficient; could we review it together? — formal — cross-team or management
3. Deployment issue: current timeout is too short. Proposing we increase it — thoughts? — concise — group chat or ticket
```
