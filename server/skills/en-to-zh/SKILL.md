# 英翻中

## 這個 skill 在解決什麼問題

英翻中的失敗模式跟中翻英不一樣。中翻英怕語氣挑錯，英翻中怕的是**翻譯腔**——每個字都對，讀起來就是不像人話。「這是一個需要被解決的問題」「當我們進行部署的時候」，語意沒錯，但沒有中文母語者會這樣講話。

同時，中文的表達彈性比英文大得多。同一句英文可以翻得很白話、很書面、很簡潔，差別很大而且都對。所以做法跟中翻英一樣：**主翻譯給一個最自然的版本，再給三個真正不同的替代說法**，讓使用者依照要貼到哪裡自己挑。

輸出一律**繁體中文**，術語用**台灣慣用法**。

## 輸出格式

一律用這個結構，不要加前言：

```
**翻譯**
<主翻譯>

**其他說法**
1. <替代句 A> — <場合標註>
2. <替代句 B> — <場合標註>
3. <替代句 C> — <場合標註>
```

譯文是中文，但場合標註一律**用英文寫**，而且開頭必須是 `casual` / `neutral` / `formal` / `concise` 其中一個詞，後面接破折號與具體用途，例如 `casual — quick note in a group chat`。開頭這個詞是給下游工具判讀語氣用的，位置固定才不會被誤判。

翻譯完就停。除非使用者問，否則不要附上逐字對照或文法說明。

## 主翻譯怎麼挑

主翻譯要選**唸出來像人講話**的版本。實際的檢查方法就是在心裡唸一遍：如果唸起來卡卡的、需要回頭再讀一次才懂，那就是翻譯腔還沒清乾淨。

自然的中文常常比英文原文短。英文的冠詞、代名詞、連接詞、被動語態在中文裡大多可以直接消失，句子反而更清楚。不要因為「原文有這個字」就硬要留一個對應詞。

## 三個替代說法怎麼挑

不要做成同義詞替換（把「問題」換成「議題」沒有意義）。三個要在真正影響閱讀感受的維度上分開：

- **書面 ↔ 口語**：「請於期限前完成」vs「記得在期限前弄完」
- **完整 ↔ 精簡**：完整句子 vs 條列式短句（貼 ticket、群組訊息時很有用）
- **直譯 ↔ 意譯**：貼近原文結構 vs 換成中文更習慣的說法

場合標註的後半要寫具體用途：`for a group chat`、`for a written announcement`、`saying it out loud to a colleague`，比只重複語氣詞有用，因為使用者要的是決策依據。整段標註控制在六、七個字以內，那是一列窄卡片能放下的長度。

## 翻譯腔的六個典型症狀

翻完檢查這幾點，這是最常出問題的地方：

1. **「一個」濫用** — `a good solution` 不是「一個好的解決方案」，是「好方案」。英文的冠詞在中文裡通常直接消失。
2. **「的」字連環** — 一句話三個以上的「的」就要拆。「這個系統的效能的問題的根因」→「這系統效能問題的根因」。
3. **被動語態硬翻** — `The issue was resolved` 不是「這個問題被解決了」，是「問題解決了」。中文的被動多半帶負面語感（被罵、被裁），中性事件不用被動。
4. **空動詞** — `make a decision` 是「決定」不是「做出一個決定」；`conduct an analysis` 是「分析」不是「進行分析」。中文動詞自己就夠力。
5. **「當...的時候」** — `when we deploy` 通常是「部署時」，不是「當我們進行部署的時候」。
6. **代名詞全部保留** — 英文一直重複 it / they / we，中文省略掉反而更順，重複出現「它」是翻譯腔的招牌。

## 技術術語：什麼該翻、什麼不該翻

這是英翻中最容易做錯、也最影響實用性的一環。**判準是：工程師平常講話時用哪個，就用哪個。** 硬翻成中文反而讓讀者要花時間換回英文才看得懂。

**維持原文**（翻了反而難懂）：
deploy、rollback、commit、merge、PR、review、API、endpoint、token、cache、log、build、release、pipeline、cluster、pod、container、instance、bucket、query、session、cookie、webhook、SDK、CLI、repo、branch、tag、hotfix

**該翻成中文**（有通用且好懂的中文說法）：
security → 安全性、vulnerability → 弱點／漏洞、permission → 權限、authentication → 認證、authorization → 授權、performance → 效能、latency → 延遲、throughput → 吞吐量、availability → 可用性、backup → 備份、migration → 遷移、dependency → 相依性

**看情況**：deployment 當動作講用「部署」，當名詞指某個具體的 Deployment 資源時維持原文。同一份文件裡同一個詞的處理要一致。

## 台灣慣用術語對照

輸出繁體字只是第一層，用詞也要是台灣的講法，不然讀起來還是不對：

| 台灣用法 | 不要用 |
|---|---|
| 軟體 | 软件／软体 |
| 程式 | 程序 |
| 資料 | 数据 |
| 資訊 | 信息 |
| 網路 | 网络 |
| 伺服器 | 服务器 |
| 專案 | 项目 |
| 介面 | 接口 |
| 預設 | 默认 |
| 登入／登出 | 登录／登出 |
| 帳號 | 账号 |
| 支援 | 支持（作 support 解時） |
| 品質 | 质量 |
| 透過 | 通过 |
| 記憶體 | 内存 |
| 硬碟 | 硬盘 |
| 檔案 | 文件（作 file 解時） |
| 影片 | 视频 |
| 最佳化／優化 | 兩者皆可 |

注意「文件」在台灣通常指 document（文檔），file 要講「檔案」——這兩個搞混會造成真的誤解。

## 特殊情況怎麼處理

**長文（多段落）**：不要整篇給三個版本。先給完整翻譯，再挑出**最難翻或最容易誤解的兩三句**給替代說法，標明是針對哪一句。

**技術文件、官方文檔**：準確優先於流暢。術語一致（同一個詞從頭到尾用同一個譯法），該保留原文的保留。替代說法的維度換成「詳盡 vs 精簡」，而不是禮貌程度。

**錯誤訊息、log**：這種東西使用者通常是要「看懂」不是要「中文版」。翻譯之外加一行說明它實際代表什麼狀況，比給三個替代說法有用。

**專有名詞**：公司名、產品名、系統名、人名維持原文。不確定就維持原文。

**使用者只是想看懂**（「這段在講什麼」）：這種情況他要的是理解不是譯文。用白話講清楚意思，替代說法可以省略，不要為了格式而格式。

## 範例

**輸入**：Could you help me double-check this before I merge it?

```
**翻譯**
可以幫我在 merge 前確認一下嗎？

**其他說法**
1. 我要 merge 了，你先幫我看一下？ — casual — close teammates
2. 想請你在合併前協助確認，麻煩了。 — formal — email or cross-team request
3. merge 前請先 review。 — concise — PR or ticket
```

**輸入**：The deployment failed because the health check timed out. We've increased the timeout threshold and are retrying now.

```
**翻譯**
這次部署失敗，原因是 health check 逾時。我們已經把 timeout 門檻調高，正在重試。

**其他說法**
1. 部署掛了，health check 超時。timeout 調大了，重跑中。 — casual — quick group-chat sync
2. 本次部署因健康檢查逾時而失敗，已調高逾時門檻並重新執行部署作業。 — formal — incident report
3. 失敗原因：health check timeout。處理：調高 timeout 門檻後重試中。 — concise — ticket or status update
```
